# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

The **dev-loop** plugin provides structured development workflow commands and agents for Claude Code. It implements three core workflows:

1. **Project Initialization**: `/init-project` - transforms user intent into comprehensive project specifications with adaptive questioning
2. **Test-Driven Development (TDD)**: `/plan` + `/tdd` - writes tests first, then implements
3. **Iterative Implementation**: `/plan` + `/implement` - implements and validates through runtime evaluation

The initialization workflow is the entry point for new projects, while TDD and iterative workflows share a common evaluation/planning foundation but differ in validation approach.

## Architecture

### Planning Document System

All workflow state lives in `.agent_planning/` directory:

**READ-ONLY files** (authoritative sources):
- `PROJECT_SPEC.md` / `PROJECT.md` - Project requirements and specifications (created by project-architect or manually)
- `ROADMAP.md` - Hierarchical project planning with phases and topics (optional, created by roadmap command)
- `STATUS-<YYYY-MM-DD-HHmmss>.md` - Current implementation state (generated by project-evaluator)
- `PLAN-<YYYY-MM-DD-HHmmss>.md` - Work backlog (generated by status-planner)

**READ-WRITE files** (working documents):
- `BACKLOG*.md`, `SPRINT*.md`, `TODO*.md` - Tracked by agents during implementation

**File retention**: Max 4 timestamped files per prefix (STATUS, PLAN). Oldest automatically deleted.

### Roadmap System

The roadmap provides high-level project organization through phases and topics:

**ROADMAP.md structure**:
- Location: `.agent_planning/ROADMAP.md`
- Format: YAML frontmatter + Markdown
- Organizes work into phases (MVP, Growth, etc.)
- Tracks topics with lifecycle states (PROPOSED → PLANNING → IN PROGRESS → COMPLETED → ARCHIVED)
- Integrates with beads epics for issue tracking
- Links to topic directories (`.agent_planning/<topic>/`)

**Topic lifecycle**:
- `PROPOSED` - Idea stage, not yet planned
- `PLANNING` - Planning files exist (STATUS, PLAN, DOD)
- `IN PROGRESS` - Active implementation
- `COMPLETED` - All acceptance criteria met
- `ARCHIVED` - Completed but no longer maintained

**Relationship to other planning docs**:
- Roadmap provides project-level organization (what to build, in what order)
- `/plan` command provides implementation-level detail (how to build it)
- Both can be used independently or together

### Scoped Evaluation System

Evaluations declare explicit scope to enable reuse and targeted re-evaluation:

**Scope Types:**
| Type | Description | Example |
|------|-------------|---------|
| `project` | Full project evaluation | `project/full` |
| `module` | Logical module/package | `module/auth` |
| `component` | Single component | `component/login-form` |
| `flow` | End-to-end data/user flow | `flow/checkout` |
| `file` | Single file | `file/src-api-users-ts` |
| `work` | Recent implementation (work-evaluator) | `work/login-feature` |
| `goal` | Specific PLAN goal (work-evaluator) | `goal/P1-user-auth` |

**File naming:**
- Scoped evaluations: `EVAL-<scope-type>-<scope-name>-<timestamp>.md`
- Full project status: `STATUS-<timestamp>.md` (backwards compatible)
- Work evaluations: `WORK-EVALUATION-<timestamp>.md`

### Confidence Levels

Findings have confidence levels based on freshness and change detection:

| Level | Meaning | Action |
|-------|---------|--------|
| **FRESH** | Just evaluated, highest confidence | Trust fully |
| **RECENT** | <7 days, no changes to scope | Trust with light verification |
| **RISKY** | Dependencies changed, or 7-30 days old | Verify key claims before relying |
| **STALE** | Files in scope changed, or >30 days | Re-evaluate or use as starting point only |

**Invalidation rules:**
1. File in scope changed → STALE
2. Direct dependency changed → RISKY
3. Config/env files changed → all scopes RISKY
4. >7 days since evaluation → RISKY
5. >30 days → STALE
6. No changes, <7 days → RECENT
7. Just evaluated → FRESH

**LLMs can still use RISKY/STALE evaluations** - they provide context and starting points. The key is knowing the confidence level to calibrate verification effort.

### Evaluation Cache (Cross-Evaluator Knowledge Sharing)

Evaluators share reusable knowledge through `.agent_planning/eval-cache/`:

```
.agent_planning/eval-cache/
├── INDEX.md                      # Topic index with timestamps
├── project-structure.md          # Project layout, key files, entry points
├── test-infrastructure.md        # Test framework, patterns, coverage
├── architecture.md               # Key patterns, data flow, dependencies
├── runtime-<scope>.md            # Runtime behavior findings per scope
└── findings-<topic>.md           # Other reusable findings
```

**REQUIRED Protocol:**
1. **Before evaluating**: Check eval-cache INDEX.md for reusable knowledge
2. **Cross-read**: project-evaluator reads work-evaluator outputs and vice versa
3. **After evaluating**: Factor out stable knowledge to cache, update INDEX.md

**What to cache** (stable knowledge):
- Project structure, directory layout, key files
- Test infrastructure, how to run tests
- Architecture patterns, data flow
- Code conventions discovered

**What NOT to cache** (ephemeral):
- Specific bug findings (keep in STATUS/EVAL/WORK-EVALUATION)
- Verdicts (COMPLETE/INCOMPLETE) - point-in-time
- Test pass/fail counts - re-run to verify

**Cache Invalidation Contract:**
- **Implementers MUST invalidate** cache entries when they modify files (primary mechanism)
- **Timestamps are the safety net** - if implementer was interrupted, evaluator checks freshness
- Two-layer validation: presence + timestamp

**Freshness (safety net for interrupted implementers):**
- FRESH (< 1 hour): Trust fully
- RECENT (< 24 hours): Trust with light spot-check
- STALE (> 24 hours): Re-validate critical findings
- ANCIENT (> 7 days): Treat as hints only

**Invalidation rules (for implementers):**
| Files Modified | Remove Cache Entries |
|----------------|---------------------|
| `src/auth/*` | `*auth*` entries |
| `tests/*` | `test-infrastructure.md` |
| Config files | `project-structure.md` |
| Architecture changes | `architecture.md` |

See `skills/eval-cache/SKILL.md` for full protocol.

### Persistent Runtime Checks

**Evaluators do NOT run ad-hoc, one-off verification commands.** Instead:

1. **Run existing persistent checks** (test suites, smoke tests, e2e tests)
2. **Document results** from those checks
3. **Specify missing checks** that implementers should create

Missing checks become implementer tasks:
```markdown
## Missing Checks (implementer should create)
1. **Smoke test** (`just smoke`) - Basic startup and health check
2. **E2E login flow** (`tests/e2e/login.test.ts`) - Error cases coverage
```

**Why persistent checks matter:**
- Reproducible across evaluation runs
- Accumulate coverage over time
- Can be run in CI/CD
- Implementers maintain them

## Complete Development Flow

### Starting From Scratch

For brand new projects or major architectural decisions:

```
User idea
     ↓
/do:init-project "Build a CLI tool for X"
     ↓
project-architect → PROJECT_SPEC.md + ARCHITECTURE.md + scaffolding (if new)
     ↓
[User reviews spec, discusses refinements if needed]
     ↓
/do:roadmap (optional) - organize work into phases
     ↓
/do:plan
     ↓
[Choose TDD or iterative workflow based on project needs]
```

The project-architect agent handles five scenarios:
1. **New project from scratch** - Creates spec and scaffolding
2. **Major architectural change** - Plans migration from current to target architecture
3. **Greenfield component addition** - Designs new subsystem within existing project
4. **Technology migration** - Plans feature-preserving rewrite to new technology
5. **Feature design from scratch** - Specifies new feature with no existing implementation

### Continuing Existing Work

For projects with established specs:

```
/do:roadmap (optional) - view project structure
     ↓
/do:plan [area of focus]
     ↓
/do:tdd OR /do:impl
     ↓
[Implementation proceeds]
```

## Core Workflows

### Workflow 0: Project Initialization (`/init-project`)

**Purpose**: Transform user intent into concrete, implementable project foundation

**When to use**:
- Starting a brand new project with no spec
- Making major architectural changes requiring new decisions
- Adding an entirely new subsystem to existing project
- Migrating to different technology
- Designing a new feature with no existing spec

**Phases**:
1. **Understand Context**: Classify scenario (new, architectural change, greenfield addition, migration, feature)
2. **Initialize**: project-architect conducts adaptive interview (15-25 questions)
3. **Validate**: Verify PROJECT_SPEC.md complete, scaffolding builds (if new project)
4. **Handoff**: Display summary, recommend `/plan` to start implementation

**Key principle**: Ask the RIGHT questions (not all questions). Provide options with tradeoffs, not arbitrary defaults. Document decisions with rationale.

**Output**:
- PROJECT_SPEC.md with 7 sections: Overview, Architecture, Tech Stack, Workflow, ADRs, Roadmap, Future Considerations
- ARCHITECTURE.md (for complex systems)
- Project scaffolding (new projects only): directory structure, skeleton files, package manager setup

### Workflow 1: TDD Workflow (`/plan` → `/tdd`)

**Phases**:
1. **Evaluate**: project-evaluator → STATUS-*.md (gap analysis, completion metrics)
2. **Plan**: status-planner → PLAN-*.md (prioritized backlog from STATUS)
3. **Test**: functional-tester → writes un-gameable functional tests
4. **Implement**: iterative-implementer (TDD mode) → implements until tests pass

**Key principle**: Tests define the contract. Implementation must pass tests through real functionality, never shortcuts.

**When to use**: Features with clear requirements that can be validated programmatically.

### Workflow 2: Non-TDD Workflow (`/plan` → `/implement`)

**Phases**:
1. **Evaluate**: project-evaluator → STATUS-*.md
2. **Plan**: status-planner → PLAN-*.md
3. **Implement Loop**:
   - iterative-implementer (manual mode) → builds functionality incrementally
   - work-evaluator → validates with runtime evidence (screenshots, logs, execution)
   - Repeat until goals achieved

**Key principle**: Validation through manual testing and runtime evaluation, not automated tests.

**When to use**: UI/visual features, exploratory work, or when tests are impractical upfront.

## Agent Responsibilities

### project-architect (initialization)
- **Input**: User intent, constraints, existing codebase (if applicable)
- **Output**: PROJECT_SPEC.md, ARCHITECTURE.md, scaffolding (if new project)
- **Mission**: Transform fuzzy user intent into concrete project foundation through adaptive questioning
- **Coverage**: 12 concern areas (identity, tech stack, structure, workflow, testing, dependencies, config, docs, deployment, errors, security, license)
- **Quality**: 15-25 questions total, explain WHY for each, present 2-3 options with tradeoffs

### project-evaluator (evaluator)
- **Input**: PROJECT_SPEC.md, codebase, previous EVAL-*.md files
- **Output**: STATUS-<timestamp>.md, EVAL-<scope>-<timestamp>.md
- **Mission**: Ruthless gap analysis. Zero-optimism assessment of what exists vs. spec.
- **Evidence**: File paths, line numbers, quantifiable metrics ("2 of 12 tools implemented")
- **Caching**: Reuses RECENT findings, spot-checks RISKY, re-evaluates STALE
- **Persistent checks**: Runs existing test suites, specifies missing checks for implementers

### status-planner (planner)
- **Input**: STATUS-*.md (latest), PROJECT_SPEC.md
- **Output**: PLAN-<timestamp>.md, SPRINT-<timestamp>.md
- **Mission**: Convert gaps into prioritized backlog with acceptance criteria
- **Cleanup**: Archives stale/contradictory planning docs

### functional-tester (TDD only)
- **Input**: PLAN-*.md, STATUS-*.md
- **Output**: Test files (tests/functional/*)
- **Mission**: Write high-level functional tests validating real user workflows
- **Anti-gaming**: Tests must verify actual behavior, not implementation details. Cannot pass with stubs.

### iterative-implementer (unified implementer)
- **Input**: PLAN-*.md, STATUS-*.md, existing tests (if any)
- **Output**: Implementation code, commits
- **Mission**: Build working functionality incrementally through careful engineering
- **Validation modes**:
  - **TDD mode**: Auto-detected when tests exist. Runs tests, iterates until all pass.
  - **Manual mode**: When no tests exist. Validates by running software manually.
- **Quality**: Clean code, proper error handling, maintainable design
- **Focus**: Real features, frequent commits, no shortcuts

### work-evaluator (Non-TDD only)
- **Input**: PLAN-*.md acceptance criteria, previous WORK-EVALUATION-*.md files
- **Output**: WORK-EVALUATION-<timestamp>.md
- **Mission**: Runtime validation - run software, capture evidence, assess goals
- **Evidence**: Screenshots and browser metadata (chrome-devtools for web apps), logs, command output
- **Caching**: References previous findings, tracks [VERIFIED-FIXED] vs [STILL-BROKEN]
- **Persistent checks**: Runs existing tests first, specifies missing checks for implementers

### product-visionary (feature proposals)
- **Input**: Current state, user needs
- **Output**: Feature proposals
- **Mission**: Design high-value features that are innovative yet pragmatic

### researcher (ambiguity resolution)
- **Input**: Specific questions with context
- **Output**: RESEARCH-<timestamp>.md with findings
- **Mission**: Investigate options, compare tradeoffs, recommend based on project context
- **Used by**: project-architect (during initialization), project-evaluator (during evaluation)

## Command Reference

### `/init-project [project description]`

Initialize a new project or make major architectural decisions.

**Usage scenarios**:
- New project: `/init-project "Build a CLI tool for validating JSON files"`
- Architectural change: `/init-project "Migrate this monolith to microservices"`
- Greenfield addition: `/init-project "Add React frontend to this backend API"`
- Technology migration: `/init-project "Migrate this project from JavaScript to TypeScript"`
- Feature design: `/init-project "Design payment processing feature for this e-commerce site"`

**Process**:
1. Detects scenario (new project vs architectural change vs greenfield vs migration vs feature)
2. Invokes project-architect agent for adaptive interview
3. Generates PROJECT_SPEC.md with comprehensive documentation
4. Creates scaffolding (new projects only)
5. Validates outputs
6. Recommends next step: `/plan`

**Output**: PROJECT_SPEC.md, ARCHITECTURE.md (if complex), scaffolding (if new)

**When to use**: Starting a project, making foundational decisions, or when no PROJECT_SPEC.md exists

### `/roadmap [topic to add]`

View roadmap tree or add topic. Provides hierarchical project planning with phases and topics.

**Usage**:
- `/do:roadmap` - Display roadmap tree view with completion metrics
- `/do:roadmap <topic>` - Add topic to roadmap with smart disambiguation

**View mode (no args)**:
- Shows phase hierarchy with status icons (active, queued, completed)
- Lists topics under each phase with lifecycle states
- Displays completion metrics from beads epics
- Quick overview of project structure

**Add mode (with args)**:
- Converts topic name to kebab-case (e.g., "User Auth" → `user-auth`)
- LLM-based similarity check against existing topics
- If similar found: shows status report, asks "Did you mean X? Or create new?"
- If new: asks which phase to add to (or creates new phase)
- Auto-creates beads epic for tracking
- Creates topic directory `.agent_planning/<topic>/`

**Integration with /plan**:
- Roadmap provides high-level organization (phases and topics)
- `/plan <topic>` provides detailed implementation breakdown
- Topic states sync automatically:
  - PROPOSED → no planning files
  - PLANNING → STATUS/PLAN/DOD exist
  - IN PROGRESS → implementation started
  - COMPLETED → all DoD met

**Example workflow**:
```bash
# View current roadmap
/do:roadmap

# Add new topic
/do:roadmap "user authentication"
# → Creates topic, beads epic, directory

# Plan the topic
/do:plan user-authentication

# Implement
/do:impl user-authentication
```

**When to use**:
- At project start to organize major features into phases
- When planning new features to see where they fit
- Periodically to review project progress
- Alternative to flat list of topics in `.agent_planning/`

**See also**: `skills/roadmap/SCHEMA.md` for ROADMAP.md format details

### `/plan [area of focus]`

Evaluate current project state and create implementation plan.

1. Runs project-evaluator → STATUS-*.md
2. Runs status-planner → PLAN-*.md

**Use**: Start any implementation workflow. Re-run after major changes to sync planning docs.

**When to use**: After initialization, or continuing existing work

### `/status [topic]`

Quick status check - no deep evaluation, just surface the current state.

Shows: WIP, uncommitted changes, in-progress work, recent plans, and next queued work.

**Use**: Fast orientation at start of session. For deep evaluation, use `/plan`.

### `/tdd [area of focus | "plan-first"]`

**TDD workflow**:
1. Optional: Run `/plan` if "plan-first" or no STATUS/PLAN exists
2. **TestLoop**: functional-tester writes tests → project-evaluator validates tests meet criteria
3. **ImplementLoop**: iterative-implementer (TDD mode) implements → project-evaluator validates implementation
4. Final: Run `/status` to show current state

**Exit conditions**:
- TestLoop: Tests meet all TestCriteria (useful, complete, flexible, automated)
- ImplementLoop: No outstanding issues with well-defined solutions

### `/implement [area of focus]`

**Non-TDD workflow**:
1. Resolves topic, finds or creates plan (chains to `/plan` if needed)
2. Gets user approval on Definition of Done (DoD)
3. **Loop**:
   - iterative-implementer → implements incrementally
   - work-evaluator → validates with runtime evidence
4. Final: Run `/status` to show current state

**Exit conditions**:
- COMPLETE: work-evaluator confirms all goals achieved
- INCOMPLETE with clear path: Continue loop
- BLOCKED: Pause, request user guidance

### `/feature-proposal [feature description]`

1. Runs product-visionary → proposal document
2. Creates forward-thinking, pragmatic feature designs

### `/research [question]`

1. Runs researcher agent to investigate ambiguities
2. Returns findings with options and recommendations

**Use**: Resolve unclear requirements or explore technology options

## Critical Rules

### For All Agents

1. **File Management**: All planning work in `.agent_planning/`. Never modify completed work files.
2. **Honesty**: No optimism, no shortcuts, no placeholders in production code
3. **Evidence**: Always cite file paths, line numbers, metrics
4. **Timestamping**: Use `YYYY-MM-DD-HHmmss` format consistently

### For Project Initialization (project-architect)

1. **Adaptive questioning**: Ask 15-25 relevant questions, not 50+. Filter by archetype.
2. **Explain WHY**: Build trust by explaining why each question matters before asking
3. **Present options**: 2-3 choices with clear tradeoffs, not arbitrary defaults
4. **Document decisions**: Capture rationale in ADR-style (decision, context, options, choice, reasoning)
5. **Progressive elaboration**: Not everything must be decided now. Mark deferrable with triggers.
6. **No arbitrary assumptions**: Ask or explain, never silently assume

### For Test Writing (TDD workflow)

1. **Never use MagicMock()** for external systems - use real objects with selective patching or `create_autospec`
2. **Never invent attributes/methods** that don't exist in real APIs
3. **Tests must fail with stubs** - un-gameable by design
4. **Validate real user workflows** - end-to-end, not implementation details

### For Implementation (Both workflows)

1. **No hardcoded test values** or test-specific branches
2. **No TODO comments** in completed code
3. **Explicit error handling** - no silent failures
4. **Real functionality** - no shortcuts to pass tests/validation

### Starting a Brand New Project

```bash
# Initialize with project-architect
/do:init-project "Build a CLI tool for task management"

# Review generated PROJECT_SPEC.md, discuss refinements if needed

# Optional: Organize into roadmap
/do:roadmap "task creation"
/do:roadmap "task listing"
/do:roadmap "task completion"

# Start implementation
/do:plan
/do:tdd  # or /do:impl
```

### Starting a New Feature (Existing Project)

```bash
# Option 1: Add to roadmap first
/do:roadmap "user authentication"
/do:plan user-authentication
/do:tdd user-authentication

# Option 2: Direct to planning
/do:plan "user authentication"
/do:tdd

# Non-TDD approach
/do:plan "dashboard UI"
/do:impl
```

### Mid-Development Status Check

```bash
# Quick overview
/do:roadmap

# Re-evaluate and update plans
/do:plan
```

### Understanding Current State

1. Read `.agent_planning/ROADMAP.md` (if exists) for high-level project structure
2. Read `.agent_planning/STATUS-*.md` (latest timestamp) for implementation gaps
3. Read `.agent_planning/PLAN-*.md` (latest timestamp) for prioritized backlog
4. Check `SPRINT-*.md` or `TODO-*.md` for immediate work items
5. Read `.agent_planning/PROJECT_SPEC.md` for requirements and architecture decisions

### Debugging Workflow Issues

**Tests pass but production fails**:
- Check functional-tester used real objects, not MagicMock with invented APIs
- Tests should fail if implementation uses wrong/non-existent APIs

**Implementation seems incomplete**:
- Check project-evaluator STATUS report for INCOMPLETE/PARTIAL/STUB_ONLY markers
- Review PLAN acceptance criteria - all must be met

**Planning docs contradict each other**:
- Use latest timestamped files (highest YYYY-MM-DD-HHmmss)
- status-planner should archive stale docs to `.agent_planning/archive/`

**Unclear what to build next**:
- Check if PROJECT_SPEC.md exists. If not, run `/init-project` to create it.
- Check if ROADMAP.md exists. If so, view it with `/roadmap` for big picture.
- If spec exists, run `/plan` to assess current state and generate backlog

- When: Web UI features in non-TDD workflow during runtime evaluation

**Integration Philosophy**: "Light touch" - chrome-devtools integrated at pivotal workflow points (runtime verification, evidence gathering) with minimal prompt additions. The work-evaluator agent uses screenshots and browser metadata as evidence alongside logs and errors when evaluating web applications.

- Tree view shows epic completion metrics

**Commands**:
- `bd create epic <topic-slug>` - Create epic
- `bd show <epic-id> --json` - Get epic details
- `bd list --epic <epic-id> --json` - Get issues

## Common Patterns

### Loop Exit Decisions

All workflows use loops with explicit exit conditions:

**Initialization**: Single-pass (user confirms spec before proceeding)
**TDD TestLoop**: Exit when tests meet all criteria (project-evaluator confirms)
**TDD ImplementLoop**: Exit when no well-defined issues remain (project-evaluator confirms)
**Non-TDD Loop**: Exit when work-evaluator returns COMPLETE status

**CRITICAL**: All loops end with an EVALUATE step - never skip evaluation.

### Agent Handoffs

Commands orchestrate multi-agent sequences:
1. Command receives user input + arguments
2. Command expands to prompt with agent invocations
3. First agent completes, produces output
4. "Only after [agent] completes, use [next agent]..." ensures sequence
5. Final agent often runs `/status` to show current state

### File Retention

Automatic cleanup prevents planning drift:
- Keep max 4 timestamped files per prefix (STATUS-*, PLAN-*)
- Delete oldest when generating new file
- Archive contradictory/stale planning docs to `.agent_planning/archive/`

## Quality Standards

### project-architect Output

- Asked 15-25 relevant questions (not 50+)
- Explained WHY for each major question category
- Presented 2-3 options with tradeoffs for major decisions
- PROJECT_SPEC.md includes all 7 main sections
- 5-10 ADRs documenting major decisions with rationale
- Roadmap is phased (MVP → Enhancement → Polish)
- Future Considerations includes deferred decisions with triggers

### project-evaluator Output

- Conservative completion percentages
- Quantified gaps ("3 of 12", "0% coverage")
- Status taxonomy: NOT_STARTED | STUB_ONLY | PARTIAL | INCOMPLETE | COMPLETE
- Confidence tags: FRESH | RECENT | RISKY | STALE on every finding
- Evaluation reuse summary: how many findings carried forward vs. fresh
- Persistent check results: table of test commands run and their status
- Missing checks section: what persistent tests implementers should create

### functional-tester Output

- Tests mirror real user workflows (CLI commands, API calls, UI interactions)
- Validate observable outcomes users see
- Multiple verification points per test (result + side effects + state)
- Real execution paths, not mocks of tested functionality

### Implementation Output

- Clean, maintainable, production-quality code
- Explicit error handling with helpful messages
- Low cyclomatic complexity
- Follows language idioms and best practices
- No placeholders, TODOs, or stub implementations

## Philosophy

**Brutal honesty saves projects**. The workflows enforce reality-based development:

- **Initialization**: Adaptive questioning → informed decisions → comprehensive specs → smooth implementation
- **Roadmap**: High-level organization → clear phases → tracked progress → visible structure
- **TDD**: Tests fail if functionality is faked → forces real implementation
- **Non-TDD**: Runtime evaluation fails if goals unmet → forces working software
- **Evaluation**: Zero-optimism gap analysis → exposes actual state
- **Planning**: Evidence-based backlog → tracks what remains

No shortcuts. No optimism. Just working software.
