
## Prompt:
NEXT: How do I organize these artifacts in a long term continuous work stream, including future roadmap and completed historical work

## Response:
Organizing Artifacts for Long-Term, Continuous Work
---------------------------------------------------

This extends the minimal control loop without adding governance overhead.

* * *

1) Repository Layout (authoritative)
------------------------------------

```
/governance
  TARGET.md
  BOUNDARY.md
  BLOCKERS.md
  METRICS.md
  HISTORY.md
  ROADMAP.md
```

Only the first four participate in the **control loop**.  
The last two are **append-only memory**.

* * *

2) Live vs Historical Artifacts
-------------------------------

### Live (mutated constantly)

These must always be small and current:

*   `TARGET.md`
*   `BOUNDARY.md`
*   `BLOCKERS.md`
*   `METRICS.md`

They define **now**.

They must never contain:

*   past decisions
*   old rationale
*   completed work

They only contain:

*   current truth
*   current constraints
*   current blockers
*   current numbers

* * *

### Historical (append-only)

These record **how we got here**.

#### `HISTORY.md`

Chronological ledger of:

*   major decisions
*   cutover changes
*   scope changes
*   retired legacy surfaces
*   resolved blockers

Format:

```
YYYY-MM-DD
  Change: …
  Reason: …
  Impact on TARGET/BOUNDARY/METRICS: …
```

This prevents:

*   re-litigating old decisions
*   plan archaeology causing drift

The agent may **read** history but must never treat it as binding.

Only the live artifacts are binding.

* * *

#### `ROADMAP.md`

Ordered list of **future slices not yet in scope**.

This is intentionally non-binding.

Format:

```
Slice
  Goal
  Expected blockers
  Dependencies
  Notes
```

Rules:

*   Items in ROADMAP are not BLOCKERS.
*   They do not justify work.
*   They are only promoted into BLOCKERS when execution begins.

This prevents:

*   future plans from pulling focus
*   agent using roadmap items to justify scope creep

* * *

3) Promotion & Retirement Rules
-------------------------------

### When work begins on something

Move it from `ROADMAP.md` → `BLOCKERS.md` with evidence.

### When something is finished

Remove it from `BLOCKERS.md`, update:

*   `METRICS.md`
*   `TARGET.md` if it changed the target
*   append a line to `HISTORY.md`

Never leave completed work in BLOCKERS or TARGET.

* * *

4) How this supports long-running work
--------------------------------------

You get three time domains:

| Domain | File(s) | Purpose |
| --- | --- | --- |
| Now | TARGET / BOUNDARY / BLOCKERS / METRICS | What must be true right now |
| Later | ROADMAP | What we might do |
| Past | HISTORY | What we already decided or did |

The agent is allowed to:

*   read Past
*   plan from Later
*   but only act on Now

That separation prevents:

*   ghost plans
*   repeated debates
*   backward pull from legacy decisions
*   roadmap-driven procrastination

* * *

5) Agent behavior over months
-----------------------------

Over a long program:

*   Live files stay small and precise.
*   HISTORY grows, but never pollutes decision-making.
*   ROADMAP evolves freely without destabilizing execution.

The minimal control loop stays intact, while institutional memory accumulates safely.

This is what makes the system viable beyond a single migration.

## Prompt:
Propose a concrete file structure whereby a 'roadmap' can include partial artifacts, and a 'completed work' bucket can contain historical artifacts

## Response:
```
/governance
  /live                         # minimal control loop (binding)
    TARGET.md
    BOUNDARY.md
    BLOCKERS.md
    METRICS.md

  /roadmap                      # non-binding, future work; can hold partial artifacts
    README.md                   # rules: promotion/retirement, naming, allowed contents
    index.md                    # ordered list of upcoming slices with links
    /slices
      /S-0001-animation-ast
        slice.md                # goal, scope, success checks, dependencies, risks (partial allowed)
        target.partial.md       # optional: delta to TARGET.md when promoted
        boundary.partial.md     # optional: delta to BOUNDARY.md when promoted
        blockers.seed.md        # optional: anticipated blockers (not authoritative)
        metrics.seed.md         # optional: proposed metrics/baselines to collect
        notes.md                # optional: exploration notes / open questions
        evidence/               # optional: screenshots, logs, links, small excerpts
      /S-0002-renderer-backend
        ...

  /completed                    # historical record; contains frozen artifacts per slice
    README.md                   # rules: immutable, how to reference from HISTORY.md
    index.md                    # table of completed slices + dates + links
    /slices
      /S-0001-animation-ast__2026-01-04
        summary.md              # what changed, why, validation performed, remaining follow-ups
        diffs.md                # pointers to PR/commit hashes, notable files touched
        TARGET.final.md         # snapshot of live TARGET.md at completion
        BOUNDARY.final.md       # snapshot of live BOUNDARY.md at completion
        BLOCKERS.final.md       # snapshot showing resolved blocker(s)
        METRICS.final.md        # snapshot with before/after
        decisions.md            # key decisions + rationale + alternatives considered
        evidence/               # logs, benchmark outputs, test results
      /S-0002-renderer-backend__YYYY-MM-DD
        ...

  HISTORY.md                    # append-only ledger of major events w/ links to completed slice folders
```

Rules implied by this structure:

*   `/governance/live/*` is authoritative and kept small.
*   `/governance/roadmap/slices/*` may contain **partial** versions of the four live artifacts as _deltas_ or _seeds_.
*   Promotion is implemented by applying `*.partial.md`/`*.seed.md` into `/live/*` and instantiating concrete entries in `/live/BLOCKERS.md` and `/live/METRICS.md`.
*   Completion freezes snapshots into `/governance/completed/slices/<id>__<date>/` (immutable).
