Convergence Mode (this works)
-----------------------------

When you hit ~80%, do this:

> “We are entering convergence mode.  
> The only goal is to eliminate blockers and make the system build and pass tests.  
> No new features. No deferrals.  
> Every remaining issue must be either fixed or explicitly resolved.”

Then force these three behaviors:

### 1) Make it enumerate blockers

> “List every remaining thing that prevents this from being correct, building, or releasable.”

This pulls all uncertainty into the present.

### 2) Make it choose one

> “Pick the single highest-risk blocker. We will resolve it now.”

No parallelism. No backlogs.

### 3) Require closure

For each blocker:

> “You must either:
>
> *   produce a patch that resolves it, or
> *   explain precisely why it cannot be resolved with available information.”
>

No TODOs.  
No future sprints.

Why this works
--------------

You are changing the internal reward landscape.

Instead of:

> “Keep making plausible progress”

You give it:

> “This task is not done until there are zero unknowns left.”

That removes the escape hatch.

The model stops trying to be clever and starts being surgical.

Bonus: turn hard parts into explicit sub-tasks
----------------------------------------------

When something is scary (migrations, test failures, data transforms), make it explicit:

> “This is a migration-risk task. You must produce:
>
> *   the forward migration
> *   the rollback
> *   and the invariant you are preserving.”
>

This reframes danger as structure, which the model can handle.

LLMs do not fail at the last 5% because they are bad at code.

And unless you explicitly tell the agent:

> “You are now responsible for closure,”

it will always try to push the stairs into the future.

## Prompt:
One thing I'm struggling with is that there might be stuff like:
- non essential UI that uses the legacy code (and must be either disconnected and ignored, or deleted or something, because it won't work until the entire refactor or migration is complete)
- tests that are testing something legacy, and the model will 'resurrect' stuff from pre-migration to try to make those tests pass.  Simply deleting the tests wholesale is...less than ideal
- Older plans that may be for an older target application state but which now have been superceded by an updated target application state

## Response:
You’ve hit the three classic “last 20%” traps in refactors: **dangling legacy dependents**, **tests that incentivize reanimation**, and **plans that are now historical artifacts**.

The way out is to stop treating the refactor as “replace X with Y” and start treating it as “operate two worlds with an explicit boundary until cutover.”

1) Non-essential UI still on legacy code
----------------------------------------

You need a **quarantine policy** with a mechanically enforceable boundary. Pick one of these, explicitly:

### A. Feature-flag quarantine (best when UI must stay shippable)

*   Put legacy UI behind a flag (or route gate) that defaults off.
*   Any callsites from new world → legacy world must go through a single “bridge module.”
*   CI enforces: “no imports from legacy packages outside the bridge.”

This lets you _ship_ while migration continues, and it stops “accidental” coupling.

### B. Disconnect + tombstone (best when UI is truly non-essential)

*   Remove entry points (routes/menu items/buttons) and replace with a tombstone UI:
    *   “This screen is temporarily unavailable during migration.”
*   Leave a single ticket reference, not TODO prose.

Key: **don’t leave the old path callable**; otherwise the agent will keep trying to make it work.

### C. Delete with a ledger (best when you’re sure)

*   Delete the UI, but add a “removal ledger” doc entry:
    *   what was removed
    *   what user capability it represented
    *   whether it will be replaced  
        This prevents later confusion and “resurrection by archaeology.”

**Agent rule that matters:**

> “Legacy UI is allowed to be broken only if it is unreachable by default and isolated behind a single bridge/flag.”

That single sentence prevents a lot of thrash.

* * *

2) Tests that cause the model to resurrect legacy code
------------------------------------------------------

This is _the_ predictable failure: the agent sees red tests and chooses the cheapest path to green, which is often “bring back the old thing.”

You fix this by making the test suite explicitly express **which reality it is validating**.

### Do a 3-way test triage (don’t delete wholesale)

For each failing test file (or suite), label it as one of:

1.  **Still-valid behavior** (should remain true post-migration)  
    → Rewrite the test to target the new API/module.  
    If the behavior moved, the test moves.
2.  **Legacy-only behavior** (intentionally going away)  
    → Convert to a _deprecation test_, not a feature test:
    *   asserts the legacy endpoint is unreachable/flagged off
    *   or asserts a specific error “Deprecated/Unavailable”  
        This keeps intent documented and prevents silent reintroduction.
3.  **Unknown / ambiguous** (behavior contract not decided)  
    → Quarantine with an explicit marker and a deadline:
    *   `@migration-pending(contract=??? owner=?? by=DATE)`  
        and exclude from CI with a _temporary allowlist_ (not a blanket skip).  
        Allowlist is key: it creates pressure to burn it down.

### Add a “no resurrection” guardrail

Make it cheap to detect reanimation:

*   Define a denylist of legacy modules/packages/symbols.
*   CI check: fail if new code imports them (except the bridge).
*   Optional: “tombstone modules” that throw on import with a message.

**Agent instruction that works:**

> “If tests fail, you may not reintroduce or rewire legacy implementations. You must either (a) migrate the test to the new world, (b) convert it to a deprecation/guardrail test, or (c) quarantine it via the explicit allowlist.”

This removes the agent’s favorite escape hatch.

3) Older plans superseded by a newer target state
-------------------------------------------------

LLMs are extremely sensitive to “old plan text” lingering in context. If it exists, they will try to satisfy it.

You need one canonical “Target State” and everything else becomes archival.

### Practical way to do this

Create a single short file (or message you paste) called something like:

**TARGET\_STATE.md (or “North Star”)**

*   what the system should look like after migration
*   what is explicitly _not_ part of the target anymore
*   migration boundary rules (what may call what)
*   current cutover strategy (flag, dual-write, adapter, etc.)
*   definition of done (build + tests + specific smoke checks)

Then add a second file:

**PLAN\_LOG.md**

*   a chronological list of plan changes (“superseded because…”)
*   links to old plans

Old plans do not get “edited.” They get **stamped**:

> “SUPERSEDED as of YYYY-MM-DD by Target State vN.”
