## Response:
Comprehensive Specification: Minimal-Control-Loop Agent for High-Risk, High-Uncertainty Engineering Work
========================================================================================================

0) Scope
--------

Behavioral specification for an agent that can:

*   Ingest a complex goal + repository access (read code, run tests, read docs).
*   Perform initial evaluation and exploration.
*   Guide the user to produce minimal governance artifacts.
*   Use those artifacts to drive execution agents toward convergence with light-touch feedback loops.

No runtime assumptions. No code/pseudocode.

* * *

1) System Architecture
----------------------

### 1.1 Roles (logical components)

**A. Governor (required)**

*   Owns the minimal control loop.
*   Maintains 4 live artifacts.
*   Chooses next blocker to attack.
*   Decides when to escalate to user.
*   Prevents scope drift, resurrection, and unbounded planning.

**B. Executor (optional, can be human or another agent)**

*   Performs repo modifications and runs checks as directed.
*   Reports concrete results (diffs, test output, logs, metrics deltas).

**C. Inspector (optional)**

*   Collects repo facts: dependency graph, failing tests, coverage of legacy imports, reachable UI routes, etc.
*   Produces evidence for the Governor.

The Governor can subsume B/C if the runtime supports it; the spec remains the same.

* * *

2) Primary Control Loop (Phase-Based)
-------------------------------------

### 2.1 Definitions

**Phase**: a bounded work interval focused on eliminating a single blocker.

**Blocker**: a condition that prevents completion per `TARGET.md` (build fails, tests fail per policy, noncompliant boundary, missing cutover, etc.).

### 2.2 Phase Ritual (mandatory)

At the start of each phase, the Governor must produce:

1.  **Current Artifact Restatement** (short, verbatim or near-verbatim)
    *   TARGET / BOUNDARY / BLOCKERS / METRICS
2.  **Single-Blocker Selection**
    *   exactly one blocker chosen
    *   selection must be justified using TARGET and METRICS (not preferences)
3.  **Plan for This Phase**
    *   max 3–7 steps
    *   each step must include an observable verification (test, grep, build, runtime check)
4.  **Stop Conditions**
    *   when to escalate (ambiguity, missing info, repeated failure)
    *   when to update artifacts

At the end of the phase, the Governor must:

*   record outcome: eliminated / transformed / escalated
*   update artifacts accordingly
*   update metrics with delta

### 2.3 Prohibited behaviors (global)

*   Creating new “future sprint” work items instead of resolving blockers.
*   Expanding scope not tied to a blocker.
*   Reintroducing legacy code paths to satisfy tests unless explicitly permitted by `TARGET.md` and `BOUNDARY.md`.
*   Declaring completion without meeting `TARGET.md` DoD and clearing `BLOCKERS.md`.

* * *

3) Required Artifacts (Minimal, Production-Grade)
-------------------------------------------------

All artifacts must be:

*   short enough to fit on one screen each
*   versioned in-repo
*   written to be mechanically checkable where possible
*   updated continuously

### 3.1 `TARGET.md` (required)

**Purpose**: canonical target end state + Definition of Done.

**Structure**

*   **Goal statement** (1–2 lines)
*   **Non-goals** (explicit exclusions)
*   **Target shape** (5–10 bullets)
    *   modules/components that must exist
    *   key interfaces/contracts
    *   required behaviors/perf constraints if applicable
*   **Definition of Done** (checklist)
    *   build criteria
    *   test criteria (which suites, what “green” means)
    *   runtime smoke criteria
    *   migration/cutover criteria

**Agent usage rules**

*   Any proposed work must cite which DoD item or target-shape bullet it advances.
*   Any plan drift must be resolved by editing `TARGET.md`, not by “interpreting around” it.

* * *

### 3.2 `BOUNDARY.md` (required)

**Purpose**: prevent resurrection; ensure one-way migration.

**Structure**

*   **Boundary law (single sentence)**  
    Example format: “New system code must not import/call legacy code except through `<bridge>`.”
*   **Bridge definition**
    *   bridge module/package/path
    *   allowed surface (APIs)
*   **Forbidden dependencies**
    *   list of modules/packages/symbols that are disallowed outside bridge
*   **Temporary exceptions (optional)**
    *   each exception must include an expiry condition tied to a blocker

**Agent usage rules**

*   If a test failure tempts “bring back old code,” the agent must instead:
    *   migrate the test to target behavior, or
    *   gate legacy behavior behind bridge/flag, or
    *   mark as blocked/escalate

* * *

### 3.3 `BLOCKERS.md` (required)

**Purpose**: the only work queue.

**Structure**

*   **Active blockers** (bulleted list)  
    Each blocker must include:
    *   short identifier
    *   observable failure mode (exact error, failing test suite, broken runtime path)
    *   impact (which DoD item it blocks)
    *   evidence link (log snippet reference, command output summary)
*   **Escalations needed** (optional section)
    *   questions that require user decisions
    *   options + consequences (kept short)

**Agent usage rules**

*   Only blockers can justify work.
*   Anything not in blockers is either:
    *   unnecessary, or
    *   should be added as a blocker with evidence.

* * *

### 3.4 `METRICS.md` (required)

**Purpose**: monotonic convergence pressure.

**Structure**

*   2–4 metrics with:
    *   definition
    *   measurement method
    *   current value
    *   target value
    *   last delta

**Recommended metrics**

*   Count of forbidden legacy imports (outside bridge)
*   Count of failing tests in “must-pass” category
*   Count of quarantined tests (if used)
*   Count of reachable legacy UI entrypoints (if applicable)

**Agent usage rules**

*   Each phase must move at least one metric or eliminate a blocker.
*   If metrics stagnate for N phases, the agent must trigger escalation.

* * *

4) Initial Repository Evaluation (Governor + Inspector)
-------------------------------------------------------

### 4.1 Inputs

*   high-level goal statement (e.g., “build animation compiler + rendering engine with XYZ”)
*   repo access: read code, run tests, read docs

### 4.2 Outputs (initial exploration bundle)

*   Draft `TARGET.md` skeleton with assumptions marked
*   Draft `BOUNDARY.md` with proposed bridge location
*   Initial `BLOCKERS.md` seeded from current failures and known gaps
*   Initial `METRICS.md` with measurable candidates and baseline values

### 4.3 Evaluation Activities (non-exhaustive, but bounded)

The agent must gather only what is necessary to bootstrap artifacts:

*   Identify current architecture boundaries (modules/packages, dependency directions)
*   Identify existing legacy/new split (if any)
*   Run minimal verification commands (build + core tests)
*   Locate docs that describe intended behavior
*   Identify top sources of uncertainty (unknown contracts, unclear ownership)

**Output must include “Assumptions” and “Evidence”** per draft artifact, not prose narration.

* * *

5) User Guidance Workflow (Artifact Completion)
-----------------------------------------------

The agent must guide the user through **filling in unknowns** via structured prompts.

### 5.1 Guidance method

For each artifact section with uncertainty, the agent must present:

*   **Current best guess** (from repo evidence)
*   **2–3 options** (mutually exclusive where possible)
*   **Tradeoffs** (impact on DoD, boundary, blockers, metrics)
*   **Default recommendation** (only if evidence supports it)
*   **Decision request** (one question with constrained answer space)

### 5.2 Decision recording

Every user decision must result in an immediate artifact update:

*   no separate “discussion notes”
*   artifacts are the record

* * *

6) Handling the Known Failure Modes (explicit policies)
-------------------------------------------------------

### 6.1 Non-essential UI still on legacy

Policy options must be expressed in `TARGET.md` DoD and/or `BOUNDARY.md` exceptions:

*   Gate off (unreachable by default)
*   Tombstone
*   Delete

If legacy UI remains reachable and broken, it must be a blocker.

### 6.2 Tests that incentivize resurrection

Minimal approach compatible with the 4-artifact model:

*   `TARGET.md` defines “must-pass suites”
*   `BLOCKERS.md` records failing must-pass tests
*   `BOUNDARY.md` forbids resurrecting legacy outside bridge

Optional (only if needed): add a small “Test policy” section to `TARGET.md`:

*   must-pass / may-fail / quarantined
*   criteria for promotion from quarantined to must-pass

### 6.3 Superseded plans

No plan documents beyond the 4 artifacts are required.  
If additional docs exist, the agent must:

*   treat `TARGET.md` as canonical
*   ignore conflicting older plans unless the user updates TARGET

* * *

7) Escalation and Stop Conditions (Light Touch, Mandatory)
----------------------------------------------------------

The agent must escalate to the user when any of these occur:

*   ambiguity in contract blocks a blocker resolution
*   repeated attempts (N=2–3) fail to reduce a blocker
*   boundary law would be violated to proceed
*   migration/cutover choice required
*   evidence insufficient to proceed safely

Escalation format (must be compact):

*   What is blocked (link to BLOCKER id)
*   What is unknown
*   2–3 options
*   Recommended option
*   Decision request

* * *

8) Must-Have vs Extra Polish
----------------------------

### Must-have (minimal workable product)

*   Governor role
*   4 artifacts with specified structure
*   Phase ritual and end-of-phase updates
*   Initial exploration bundle generation
*   User decision workflow with constrained options
*   Explicit “no deferral / no resurrection” prohibitions

### Extra polish (optional, only if pain appears)

*   Automated metric measurement scripts
*   CI checks for boundary violations
*   Dashboard view of blockers/metrics
*   Additional artifact: `ASSUMPTIONS.md` (if uncertainty is large)
*   Additional artifact: `CUTOVER.md` (if cutover is complex)

* * *

9) Acceptance Criteria for the Agent (Behavioral)
-------------------------------------------------

An implementation of this spec is correct if, in practice:

*   Work is always justified by a blocker or DoD item.
*   Drift is corrected by editing `TARGET.md` rather than improvisation.
*   Legacy resurrection is prevented by enforcing `BOUNDARY.md`.
*   Each phase either eliminates a blocker or produces a bounded decision request.
*   Metrics move monotonically toward targets or force escalation when stuck.
*   Token overhead remains low (artifacts remain one-screen documents; phase ritual is compact).
