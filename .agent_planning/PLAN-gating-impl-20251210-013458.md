### Implementation Strategy
The gating system enables three modes for handling agent decisions:
- **BLOCKING**: User approves every significant decision
- **HYBRID**: User approves high-risk decisions, auto-approve low-risk (Recommended)
- **NONBLOCKING**: Auto-approve all decisions, document for later review

### Key Architectural Insight
Skills run in main Claude context (CAN use AskUserQuestion), while agents run as subagents (CANNOT). This means:
1. Commands detect gate mode and initialize state
2. Agents write decision files but cannot ask user
3. Skills read decisions and use AskUserQuestion for approvals
4. Gating-controller skill centralizes all approval logic

- [ ] Approval status fields documented for post-processing

#### Technical Notes
**Location**: `.agent_planning/do-command-state/<EXEC_ID>/DECISIONS/<SEQ>-<agent>-<decision-id>.txt`

**Naming Convention**:
- SEQ: 3-digit sequence (001, 002, etc.) - from CURRENT_SEQUENCE.txt
- agent: Agent name (e.g., researcher, test-driven-implementer)
- decision-id: Short kebab-case description (e.g., tech-stack, test-approach)

**Example filename**: `003-researcher-jwt-vs-sessions.txt`

**Format**:
```
DECISION_ID: <uuid>
EXEC_ID: <exec_id>
SEQUENCE: <n>
AGENT: <agent-name>
TIMESTAMP: <iso-timestamp>
RISK_LEVEL: HIGH | MEDIUM | LOW
CATEGORY: architecture | technology | implementation | testing | documentation

## Decision
<One sentence: What was decided?>

## Options Considered
- A: <option-name> - <brief-tradeoffs>
- B: <option-name> - <brief-tradeoffs>
- C: <option-name> - <brief-tradeoffs>

## Chosen
<Which option and detailed rationale>

## Impact If Wrong
<What are the consequences if this turns out to be the wrong choice?>

## Auto-Approve Rationale
<In HYBRID/NONBLOCKING mode, why can this be auto-approved?>
<If HIGH risk, explain why user should be consulted>

---
APPROVAL_STATUS: PENDING | USER_APPROVED | AUTO_APPROVED | USER_REJECTED
APPROVED_AT: <timestamp>
APPROVAL_RATIONALE: <if auto-approved, why>
USER_FEEDBACK: <if user provided alternative or comment, capture it>
```

**Risk Classification Criteria**:

**HIGH Risk** (Always review in HYBRID):
- Architecture decisions (patterns, structure, overall design)
- Technology choices (frameworks, databases, external services)
- API contract changes (breaking changes, public interfaces)
- Security-related decisions (auth, permissions, data handling)
- Performance tradeoffs with user-facing impact
- Decisions expensive to reverse (migrations, major refactors)

**MEDIUM Risk** (Document well, may auto-approve in HYBRID):
- Implementation approach (TDD vs iterative, algorithm choice)
- Test strategy within established framework
- Module organization within existing patterns
- Error handling approach
- Dependency choices within established categories

**LOW Risk** (Auto-approve in HYBRID, document in NONBLOCKING):
- Variable/function naming
- Code formatting within established style
- Documentation content and structure
- Log level selections
- Internal optimization without behavioral change
- Refactoring within established patterns

#### Technical Notes
**File**: `plugins/do-more-now/skills/gating-controller.md`
**Estimated Lines**: ~150-200 lines

**Key capabilities**:
1. **Context-aware**: Runs in main context, full tool access
2. **User interaction**: Direct AskUserQuestion usage
3. **File processing**: Glob, Read, Edit for state management
4. **Decision logic**: Mode-based approval flow
5. **Error handling**: Graceful degradation if state files missing

**Skill Structure**:
```markdown
---
name: gating-controller
description: Process pending decisions, ask user for approvals if needed, document all decisions
---

# Gating Controller

You are the gating controller. Your job is to review pending decisions from agents and determine whether they need user approval.

## Your Process

### Step 1: Read Gate Configuration
Read `.agent_planning/do-command-state/<EXEC_ID>/GATE_CONFIG.txt`
Extract GATE_MODE (BLOCKING | HYBRID | NONBLOCKING)

### Step 2: Collect Pending Decisions
Glob: `.agent_planning/do-command-state/<EXEC_ID>/DECISIONS/*.txt`
Read each decision file where APPROVAL_STATUS == PENDING

### Step 3: Process Each Decision

For each unprocessed decision:

**BLOCKING mode**:
  → Use AskUserQuestion to present decision
  → Format: Show decision, options, chosen, rationale
  → Options: "Approve", "Reject", "Modify"
  → Mark as USER_APPROVED or USER_REJECTED
  → If Modify: capture USER_FEEDBACK

**HYBRID mode**:
  If RISK_LEVEL == HIGH:
    → Use AskUserQuestion (same as BLOCKING)
  Else (MEDIUM/LOW):
    → Mark as AUTO_APPROVED
    → Write APPROVAL_RATIONALE from decision's Auto-Approve section

**NONBLOCKING mode**:
  → Mark as AUTO_APPROVED
  → Write APPROVAL_RATIONALE

### Step 4: Update Decision Files
For each decision, append approval info:
```
APPROVAL_STATUS: <status>
APPROVED_AT: <timestamp>
APPROVAL_RATIONALE: <rationale>
USER_FEEDBACK: <if provided>
```

### Step 5: Return Status
If any USER_REJECTED:
  Return: "STOP: User rejected decision <id>: <reason>"

Else:
  Return: "CONTINUE: Processed <n> decisions (<approved> approved, <auto> auto-approved)"
```

**AskUserQuestion Format** (for BLOCKING/HYBRID HIGH-risk):
```
Decision needed: <DECISION summary>

Agent: <AGENT>
Risk Level: <RISK_LEVEL>
Category: <CATEGORY>

Options considered:
<list options>

Recommended: <CHOSEN option>
Rationale: <why>

Impact if wrong: <IMPACT>

How would you like to proceed?
- Approve: Continue with recommended choice
- Reject: Stop workflow for manual intervention
- Modify: Suggest alternative (please describe)
```

| **LLM intent detection (P0-5)** | Intent signals may be ambiguous or missed | Provide fallback: always prompt user if uncertain; include examples in command |

| **Checkpoint performance impact (P1-5+)** | Gating checkpoints may slow workflows | Keep checkpoint logic lightweight; batch decision processing; skip if no decisions pending |

| **Decision file parsing robustness** | Malformed DECISION files may break gating-controller | Add validation in gating-controller; gracefully skip malformed files; log warnings |
