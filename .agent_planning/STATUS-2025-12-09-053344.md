## Semantic Validation (Essence vs. Noise)

### What Is The ESSENCE?

**Evaluators exist to answer ONE question**: "Does this work for real users?"

**The answer requires**:
1. **Evidence** (not opinions): Run it, capture results
2. **Honesty** (not optimism): Report what actually happened
3. **Clarity** (not confusion): Specific issues with locations

**That's it.** Everything else is support structure.

### Current System Assessment

#### ✅ What's Working (KEEP)

**1. Profile-based validation** (evaluation-profiles skill)
- **Why it works**: Prevents wasting time on irrelevant checks
- **Evidence**: agent-prompt profile correctly skips runtime testing, focuses on structural validation
- **Impact**: 50-70% time savings claimed (SKILL.md:12-13)
- **Feedback loop**: Profile determines checks → evaluator runs only relevant validations → focused output

**2. Two-evaluator split** (project vs work)
- **Why it works**: Different scopes need different approaches
  - project-evaluator: Comprehensive, slower, STATUS→PLAN
  - work-evaluator: Focused, faster, tight IMPLEMENT→EVALUATE loop
- **Evidence**: work-evaluator uses chrome-devtools for UI evidence, project-evaluator doesn't
- **Feedback loop**: Scope determines evaluator → evaluator uses appropriate tools → output feeds correct consumer

**3. Core assessment areas** (project-evaluator.md:39-127)
- **Why they work**: Cover the actual failure modes (runtime, data flow, test quality, blind spots, ambiguity)
- **Evidence**: Each area maps to real LLM failure pattern
- **Lean**: 7 areas, each 5-15 lines of guidance = ~100 lines total

**4. Research integration** (both evaluators)
- **Why it works**: When evaluator finds ambiguity, researcher resolves it, evaluator confirms → continues
- **Evidence**: project-evaluator.md:218-270 (research evaluation mode), /do:plan command triggers auto-research
- **Feedback loop**: Ambiguity found → research → decision made → implementation proceeds with clarity

#### ❌ What's Broken (FIX)

**Problem 1: "Skip if difficult" escape hatch** (line 37 in both evaluators)
```markdown
If a validation is difficult or taking >30 seconds without progress, **skip it**
```

**Why broken**: Subjective, time-based, provides easy out. LLM hits obstacle → "this is difficult" → skip → false confidence.

**User requirement**: "REMOVE time-based skipping" (PLAN:12-13, 169-180)

**But existing solution is TOO COMPLEX**: P0-4 proposes deterministic feasibility assessment, escalation templates, VALIDATION_DEBT.md ledger, user confirmation tracking. That's 4-5 mechanisms to replace 1 line.

**Essence**: LLM should say "I can't verify this automatically" and explain what the user should check. That's ONE thing, not a framework.

**Problem 2: Redundant automation recommendations** (lines 282-299 in both evaluators)

**Why broken**: Every manual check triggers "suggest how to automate" recommendation. This is REACTIVE (after the fact) instead of PROACTIVE (build tests first).

**Evidence**:
- TDD workflow ALREADY has functional-tester building tests BEFORE implementation
- Non-TDD workflow focuses on speed, adding test burden slows the loop
- Automation recommendations in STATUS files are rarely acted on (no tracking)

**Essence**: Tests come from functional-tester (TDD) or don't come at all (non-TDD). Evaluators shouldn't be test designers.

**Problem 3: Kicking work back is verbose** (lines 300-314 in both evaluators)

**Why broken**: 13-line example showing bad vs good feedback. Pedagogically correct but token-heavy.

**Evidence**: P2-3 in existing plan identifies this (~100-150 token savings)

**Essence**: One terse example is enough. LLMs understand "be specific" without 13 lines.

#### ⚠️ What's MISSING (ADD - but keep lean)

**Missing 1: "I couldn't verify X" explicit output**

**Why missing**: Evaluators currently have two modes:
1. ✅ Verified (evidence present)
2. [nothing] (skipped without noting)

**Gap**: When validation is skipped, STATUS doesn't document what wasn't checked. User doesn't know what's unverified.

**Lean solution**: Add "⚠️ NOT VERIFIED" status with reason. One table section in STATUS template.


**Impact**: User knows explicitly what they need to check. No complex ledger, no tracking across sessions, just current-state transparency.

**Missing 2: "Runtime trumps tests" principle is buried**

**Why missing**: Critical principle at line 275 in project-evaluator, easy to miss

**Evidence**: Existing plan P1-3 identifies this, proposes elevating to H2 section

**Lean solution**: Move to top, make prominent. No new framework, just reorganize.

## System Design Analysis (The Holistic View)

### The Feedback Loop Architecture

```
USER REQUEST
     ↓
COMMAND (/do:plan, /do:it)
     ↓
EVALUATOR (project-evaluator or work-evaluator)
     ↓
STATUS/WORK-EVALUATION file (evidence, gaps, recommendations)
     ↓
PLANNER (status-planner) [only for /do:plan]
     ↓
PLAN file (prioritized backlog)
     ↓
IMPLEMENTER (test-driven-implementer or iterative-implementer)
     ↓
CODE CHANGES
     ↓
EVALUATOR (validates) → LOOP or EXIT
```

**This loop ALREADY WORKS.** Evidence:
- Commands orchestrate agent sequences (plan.md:15-33, it.md:28-69)
- Evaluators produce STATUS/WORK-EVALUATION files
- Implementers read those files (iterative-implementer.md:22)
- Loop repeats until exit condition

### Where Feedback Loops Are Strong

**1. TDD TestLoop** (it.md:35-50)
```
functional-tester → project-evaluator → [meets criteria?] → exit or loop
```
**Why strong**: Clear exit condition (TestCriteria met), evaluator judgment, no manual intervention

**2. Non-TDD Implementation Loop** (it.md:77-98)
```
iterative-implementer → work-evaluator → [verdict?] → COMPLETE/INCOMPLETE/PAUSE/BLOCKED
```
**Why strong**: Runtime evidence required, verdict taxonomy clear, PAUSE stops bad work

**3. Auto-research on PAUSE** (plan.md:20-27, it.md:46, 65, 96)
```
evaluator finds ambiguity → PAUSE → researcher → evaluator assesses research → decision → continue
```
**Why strong**: Ambiguity doesn't block progress, research is automatic (3 iteration limit), user only involved if unresolvable

### Where Feedback Loops Are Weak (Gaps)

**Gap 1: No feedback from "skip if difficult" decisions**

**Current**: Evaluator skips validation → nothing in STATUS → implementer/user unaware

**Missing loop**: Skip decision → "Not Verified" section → user sees gap → user validates OR researcher investigates automation

**Why it matters**: Hidden unknowns are worse than known unknowns. User can't act on what they don't see.

**Gap 2: Automation recommendations don't loop back**

**Current**: Evaluator suggests "automate with Playwright" → recommendation in STATUS → [nothing happens]

**Missing loop**: Recommendation → tracked → functional-tester implements → validated

**Why it matters**: Good ideas are worthless if never acted on. But adding tracking adds weight.

**Alternative**: REMOVE automation recommendations from evaluators. If tests are needed, TDD workflow builds them. Non-TDD workflow intentionally skips tests for speed.

**Gap 3: Test quality verification is advice, not requirement**

**Current**: "Quick test: Break something obvious" (line 70) = suggestion

**Missing loop**: Test quality check → evidence in STATUS → implementer validates → tests are trustworthy

**Why it matters**: Worthless tests create false confidence. If tests aren't verified, don't trust them.

### What's WRONG About The Plan

**Violation 1: Complexity over simplicity**

The plan adds FIVE new frameworks:
1. Evidence tables (P0-1)
2. Confidence scoring system (P0-2)
3. Test quality verification protocol (P0-3)
4. Deterministic feasibility assessment (P0-4)
5. Workflow gates with 3 modes (P1-1)

**User directive**: "KEEP IT SIMPLE, LEAN, FLEXIBLE"

**Reality**: This is the OPPOSITE of lean. Each framework has templates, rules, integration points, documentation.

**Violation 2: Heavy process over light touch**

Example: P0-4 (Replace "skip if difficult")
- **Current**: 1 line guidance "skip it and note why"
- **Proposed**: Deterministic feasibility assessment, three-outcome taxonomy (CAN_VALIDATE/CANNOT_VALIDATE/USER_VALIDATES), escalation templates, VALIDATION_DEBT.md ledger, user confirmation tracking across sessions
- **Ratio**: 1 line → ~50 lines of framework + file management

**User directive**: "Light touch means the SYSTEM should be guided by feedback loops towards the right solution"

**Reality**: This is HEAVY touch. It replaces judgment with process.

**Violation 3: Enforcement over feedback**

The plan's philosophy:
- **P0-1**: REQUIRED runtime evidence (if missing, evaluation INVALID)
- **P0-2**: Confidence levels MUST be used
- **P0-3**: Test quality verification REQUIRED (if skipped, mark UNKNOWN)
- **P1-1**: Workflow gates BLOCK proceeding if validation insufficient

**User directive**: "Feedback loops over brute force"

**Reality**: These are BRUTE FORCE mechanisms. They BLOCK progress instead of GUIDING it.

**Violation 4: Solving symptoms, not root cause**

**Root cause**: LLMs take shortcuts when validation is hard or unclear

**Symptom 1**: Tests pass but software broken
**Symptom 2**: Evaluator says COMPLETE without evidence
**Symptom 3**: Implementation proceeds with hidden unknowns

**Plan's approach**: Add enforcement (REQUIRED, INVALID, BLOCKING) to prevent symptoms

**Better approach**: Make the RIGHT thing EASIER than the WRONG thing
- If providing evidence is easier than explaining why you didn't → evidence happens
- If noting "I couldn't verify X" is expected → gaps become visible
- If distinguishing "verified by running" vs "verified by reading" is natural → honesty emerges

## Clarification Needed Before Proceeding

### Question 1: Accept lean alternative over existing plan?

- Philosophy: Enforce correctness through REQUIRED/INVALID/BLOCKING mechanisms
- 4-6 weeks effort, +100-150 lines

**Lean alternative**:
- 6 changes, 0 new frameworks (template extensions only)
- Philosophy: Make the right thing easy, wrong thing visible (transparency over enforcement)
- 2-4 days effort, -30 lines net

**Options**:
- **Option A**: Proceed with lean alternative (Changes 1-7)
  - Tradeoffs: Simpler but relies on evaluator judgment (LLM must choose to document skips)
  - Aligns with: User's lean, simple, light touch directives

  - Tradeoffs: More robust enforcement but heavyweight, complex
  - Aligns with: Preventing false positives through hard requirements

  - Tradeoffs: Risk of mixing philosophies (enforcement + transparency may conflict)

### Question 2: Is the FILE-based feedback loop architecture the right level?

**Context**: Current system uses files (STATUS, PLAN, WORK-EVALUATION) as handoff points between agents. This is visible, auditable, debuggable. But it's also heavyweight compared to in-memory state.

**Current approach**:
- Every evaluator writes a timestamped file
- Implementers read most recent file
- User can inspect files to understand state
- File retention: keep 4 most recent per prefix

**Options**:
- **Option A**: Keep file-based (current)
  - Tradeoffs: Visible, debuggable, persistent | Heavyweight, file management complexity
- **Option B**: Move to in-memory state (agent responses only)
  - Tradeoffs: Lighter, simpler | Opaque, hard to debug, lost on error
- **Option C**: Hybrid (summary in-memory, full detail in files)
  - Tradeoffs: Best of both? | Complexity of maintaining two formats

**Impact of wrong choice**:
- If B chosen → lose visibility, debugging becomes difficult, user can't audit
- If A kept but too heavyweight → file proliferation, management overhead

**Current assessment**: FILE-BASED IS CORRECT for this system. The "weight" is in generating complex file content, not in writing files. Making content leaner addresses the real issue.

**No change needed**: Architecture is sound. Focus on content quality, not architecture.
