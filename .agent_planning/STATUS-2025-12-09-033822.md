## Validation Analysis: Useful vs. Wasteful

### Category 1: ALWAYS Useful (Do Every Time)

| Validation | Why Useful | Time Cost |
|-----------|------------|-----------|
| Grep for TODO/FIXME in "complete" code | Catches fake completeness | LOW (1-2 sec) |
| Check file exists at expected path | Catches missing implementation | LOW (<1 sec) |
| Count assertions in tests | Catches empty test files | LOW (1-2 sec) |
| Verify error handling present | Catches silent failures | LOW (grep, 2-3 sec) |

**Recommendation**: KEEP these. Fast, always relevant, high signal.

---

### Category 2: CONDITIONALLY Useful (Do If Relevant)

| Validation | When Useful | When Wasteful | Time Cost |
|-----------|-------------|---------------|-----------|
| Runtime testing | Runnable software exists | Prompts, configs, incomplete code | HIGH (30sec-2min) |
| Test the tests (bug injection) | Tests exist and pass | No tests, tests already failing | HIGH (1-2 min per function) |
| Follow the data (6-step trace) | Data-heavy features | Non-data features, prompts | MEDIUM (30sec-1min) |
| LLM blind spots (pagination) | List/pagination features | Non-paginated features | MEDIUM (30sec) |
| LLM blind spots (second run) | Stateful software | Stateless operations | MEDIUM (30sec-1min) |
| LLM blind spots (cleanup) | File/resource operations | Pure logic, prompts | MEDIUM (30sec) |

**Recommendation**: Make these OPTIONAL with clear triggers:
- "IF tests exist and pass → test the tests"
- "IF feature involves lists → check pagination"
- "IF runnable software → attempt runtime test"

---

### Category 3: RARELY Useful (Only On Request)

| Validation | Why Rarely Useful | When To Do It | Time Cost |
|-----------|------------------|---------------|-----------|
| Concurrent access testing | Requires test harness | User reports race conditions | HIGH (2-5 min) |
| Memory leak profiling | Requires instrumentation | User reports memory issues | VERY HIGH (5-10 min) |
| Performance benchmarking | Needs baseline | User sets performance goals | HIGH (2-5 min) |
| Security audit | Specialized knowledge | Pre-release checklist | VERY HIGH (10-30 min) |

**Recommendation**: REMOVE from default checklist. Add as `/do:audit` or user-requested validations.

## Architectural Issues

### Issue 1: Checklists Don't Adapt to Context

**Current Design**: Fixed set of assessment areas applied to every evaluation.

**Problem**: Evaluating a Claude Code plugin prompt is VERY DIFFERENT from evaluating a web application, but both get the same checklist:
- Plugin prompt: No runtime, no data flow, no pagination, no cleanup
- Web app: Has runtime, data flow, pagination, cleanup

**Evidence**: STATUS-2025-12-07-225946.md spends time marking checklist items as "N/A" or "[?] not applicable".

**Better Design**: Context-aware evaluation profiles:
- Profile: "CLI Tool" → runtime, error handling, help text, exit codes
- Profile: "Web UI" → runtime, data flow, user flows, browser testing
- Profile: "Agent/Prompt" → structure, clarity, tool usage, examples
- Profile: "Library/API" → interface design, error handling, edge cases

**Benefit**: Only check what matters for the thing being evaluated.

---

### Issue 2: "Run Before Reading" Philosophy Is Too Rigid

**Current Design**: "Always try to use the software before inspecting code. No exceptions."

**Problem**:
- Forces evaluators to attempt runtime testing even when infeasible
- OR spend time justifying why runtime testing was skipped
- Doesn't account for non-runnable artifacts (prompts, configs, docs)

**Evidence**: WORK-EVALUATION-2025-12-07-231430.md lines 84-91 explicitly documents why runtime testing is impossible and creates static checklist instead.

**Better Design**: Tiered validation strategy:
1. **Tier 1 (always)**: Static checks (files exist, no TODOs, error handling present)
2. **Tier 2 (if runnable)**: Runtime checks (software starts, basic flow works)
3. **Tier 3 (if time/feasible)**: Deep checks (edge cases, performance, concurrency)

**Benefit**: Evaluators spend time on what's actually feasible, not fighting the "no exceptions" rule.

---

### Issue 3: No Incremental Validation

**Current Design**: Each evaluation starts from scratch with full assessment protocol.

**Problem**:
- TestLoop EVAL #1: Check test quality
- ImplementLoop EVAL #2: Check test quality AGAIN (tests didn't change)
- Final EVAL #3: Check test quality YET AGAIN (tests still didn't change)

**Better Design**: Stateful evaluation with change detection:
```
EVAL #1:
  - Check test quality → cache result + file hash
  - Output: "Tests: GOOD (cached for future evals)"

EVAL #2:
  - Check if test files changed (compare hash)
  - If unchanged: "Tests: GOOD (from cache)"
  - If changed: Re-check test quality

EVAL #3:
  - Check if test files changed
  - If unchanged: "Tests: GOOD (from cache, verified in EVAL #1)"
```

**Benefit**: Avoid redundant work. Only re-check what could have changed.

### Issue 4: Validation Work That Should Be User's Decision

**Current Design**: Evaluators attempt to validate everything, including things that are subjective or require user input.

**Examples from STATUS-2025-12-07-225946.md**:
- "Cleanup policy: Archive after N days? (NEEDS DECISION)"
- "What should happen on auth failure? Need error message design."
- "Session timeout: 30min hardcoded. Is this correct?"

**Problem**: Evaluator spends time identifying ambiguities, but then what?
1. Flag as ambiguity → document in STATUS
2. Trigger researcher to explore options
3. Evaluator assesses research
4. Someone still needs to make decision (user or evaluator?)
5. If evaluator decides, was it the right call?

**Better Design**: Distinguish validation types:
- **Objective validation**: "Does it work?" → Evaluator's job
- **Subjective validation**: "Is 30min the right timeout?" → User's job, ASK
- **Impossible validation**: "Is this secure?" → Requires expert, ASK for test plan

**Benefit**: Evaluators focus on "does it work" not "did implementer guess the requirements correctly".
