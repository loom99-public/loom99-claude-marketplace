## Architectural Evolution Analysis

### Generation 1: do-more-now (Baseline)

**Philosophy**: One command per function. Explicit and discoverable.

**Command Structure**:
```
/do:plan              → Evaluate + plan
/do:status            → Quick status check
/do:audit             → Deep audit
/do:init-project      → Initialize project
/do:feature-proposal  → Feature design
/do:chores            → Maintenance
/do:it                → Implementation
/do:peek              → Fast codebase questions
/do:learn             → Internal research
/do:research          → External/market research
/do:track             → Backlog capture
```

**Strengths**:
- Zero ambiguity - each command has one purpose
- Autocomplete shows all capabilities
- Flat learning curve

**Weaknesses**:
- 11 commands in autocomplete
- Cognitive load: "Which command do I need?"
- Command namespace pollution
- Functionality overlap (status vs audit, learn vs research)

**Evidence**: /Users/bmf/icode/loom99-claude-marketplace/plugins/do-more-now/commands/ contains 11 separate .md files

### Generation 2: do2 (Mode Detection)

**Philosophy**: Fewer commands, mode detection via first-word parsing.

**Command Structure**:
```
/do2:plan [mode] [focus]
  Modes: init, audit, status, feature, default

/do2:it [mode] [task]
  Modes: refactor, debug, fix, review, test, chores, tdd, iterate, default

/do2:peek [question]

/do2:learn [mode] [topic]
  Modes: market, external, default (internal)

/do2:track [task]
```

**Mode Detection Logic** (from /Users/bmf/icode/loom99-claude-marketplace/plugins/do2/commands/plan.md:14-23):
```
| First word | Mode | Action |
|------------|------|--------|
| `init` | Initialize | Create new project spec via project-architect |
| `audit` | Deep audit | Exhaustive evaluation via project-evaluator (audit mode) |
| `status` | Quick status | Fast diagnostic via project-evaluator or work-evaluator |
| `feature` | Feature proposal | Design new feature via product-visionary |
| *(anything else)* | Default | Full evaluate + plan cycle |
```

**Strengths**:
- 55% reduction in visible commands (11→5)
- Natural language: `/do2:plan audit security` reads clearly
- Mode keywords act as hints: users learn modes through usage
- Maintains full do-more-now functionality

**Weaknesses**:
- Mode detection is invisible - users must read docs to discover modes
- First-word parsing is deterministic but not obvious
- "Hidden features" problem: `/do2:it` has 8 modes
- Mode keywords not validated (typos silently fall through to default)

**Migration Impact**:
```
/do:status       → /do2:plan status
/do:audit        → /do2:plan audit
/do:init-project → /do2:plan init
/do:research     → /do2:learn market
/do:chores       → /do2:it chores
```

**Evidence**: /Users/bmf/icode/loom99-claude-marketplace/plugins/do2/CLAUDE.md documents mode tables

## Layered Architecture Assessment

### Current State

**Problem**: Functionality is **hidden inside multipurpose commands**.

Example (do2):
```
/do2:it [task]
  - Implements features
  - Refactors code
  - Debugs issues
  - Fixes bugs
  - Reviews code
  - Adds tests
  - Runs chores
  - Routes to TDD or iterative workflow
```

A single command does **8+ different things** depending on the first word.

**Cognitive Load**: Users must:
1. Remember `/do2:it` handles all implementation
2. Know which keywords trigger which mode
3. Understand what each mode does

### Proposed: Layered Architecture

**Concept**: Split into **separate plugins** where each plugin is a focused layer.

#### Layer Proposal

```
Base Layer (do-core)
├── /do:plan          → Evaluate + plan
├── /do:status        → Quick status
└── /do:peek          → Fast questions

TDD Layer (do-tdd)
├── /tdd:test         → Write tests
├── /tdd:impl    → Implement to pass tests
└── /tdd:commit       → Commit TDD cycle

Iterative Layer (do-iter)
├── /iter:impl   → Implement incrementally
├── /iter:verify      → Run + validate
└── /iter:commit      → Commit iteration

Research Layer (do-research)
├── /research:learn   → Internal research
└── /research:market  → External research

Visual Layer (already exists: visual-iteration plugin)
├── /screenshot
├── /feedback
└── /iterate-loop

Maintenance Layer (do-maint)
├── /maint:audit      → Deep audit
├── /maint:chores     → Cleanup
├── /maint:refactor   → Restructure
└── /maint:review     → Code review

Debug Layer (do-debug)
├── /debug:investigate → Root cause analysis
└── /debug:fix         → Fix implementation
```

#### Benefits

**1. Minimal API Surface Per Layer**

- Each plugin has 2-5 commands max
- User installs only what they need
- Autocomplete shows relevant commands only

**2. Clear Boundaries**

- TDD workflow? Install do-tdd
- Iterative workflow? Install do-iter
- Don't need both? Don't install both

**3. Reduced Cognitive Load**

- No mode detection
- No intent parsing
- Command names are explicit: `/tdd:test` not `/do:it tdd write tests`

**4. Independent Evolution**

- Update TDD layer without touching iterative layer
- Add new debug commands without affecting planning
- Version layers independently

**5. Discoverability**

- All commands visible in autocomplete
- Namespace indicates purpose: `/tdd:*`, `/iter:*`, `/debug:*`

#### Drawbacks

**1. Plugin Management Complexity**

- Users must know which plugins to install
- Dependency management: does do-tdd require do-core?
- Version drift: do-tdd v0.2 + do-core v0.1 compatibility?

**2. Cross-Layer Dependencies**

- All layers need project-evaluator agent
- Shared agents = duplication or extraction to shared plugin?
- If shared plugin: now users need 3 plugins (core + layer + shared-agents)

**3. Installation Friction**

- Current: 1 plugin install
- Layered: 2-4 plugin installs depending on workflow

**4. Discoverability of Layers**

- How do users know do-tdd exists?
- Marketplace must surface related plugins
- Documentation must explain layer relationships

**5. Namespace Proliferation**

- 6 layers × 3-5 commands = 18-30 total commands across all layers
- Back to the original problem if users install all layers

#### Cross-Layer Dependency Analysis

**Agents are shared** - all layers need:
- project-evaluator
- work-evaluator
- researcher
- status-planner

**Options**:

**Option A**: Duplicate agents in each layer plugin
- **Pro**: No dependencies, each layer is standalone
- **Con**: 3,664 lines × 6 layers = 21,984 lines of duplication

**Option B**: Extract to shared `do-agents` plugin
- **Pro**: Single source of truth, 3,664 lines total
- **Con**: All layers depend on do-agents, installation complexity

**Option C**: Agents in base layer (do-core), other layers depend on it
- **Pro**: Core is required anyway, no extra plugin
- **Con**: Tight coupling, can't update do-tdd without compatible do-core

### Recommendation: Keep Unified Architecture

**Rationale**:

1. **Complexity explosion**: Layered approach trades "hidden features" for "plugin explosion"
2. **Dependency hell**: Shared agents create tight coupling or duplication
3. **Installation friction**: 1 plugin install vs 3-4 plugin installs is significant UX degradation
4. **Current API is actually good**: 5 commands (do2/do3) is reasonable, not overwhelming

**Evidence**:
- do2 successfully reduced API from 11→5 commands (55% reduction)
- do3 skills approach enables extensibility without API growth
- Mode detection is learnable: power users discover modes through docs

**Counter-evidence**:
- Layered approach would enable A La Carte installation
- Visual-iteration plugin already exists as separate layer (precedent)

**Verdict**: **Unified plugin (do2 or do3 model) is superior** unless:
- User research shows "I only need TDD, not research" is a common pain point
- Plugin installation friction is negligible (currently unknown)
- Marketplace provides strong "related plugins" discovery


### Recommendation 4: Extract Common Layer (Optional)

**If** layered architecture is pursued, start with:

**Step 1**: Extract agents to `do-core` plugin
- 10 agents
- Minimal commands: `/do:evaluate`, `/do:plan`

**Step 2**: Create focused layer plugins
- `do-tdd`: TDD workflow (depends: do-core)

**Step 3**: Evaluate adoption
- If users install both do-tdd and do-iter, layering failed (should be unified)
- If users install only one, layering succeeded

**Hold**: Don't proceed with full layered architecture until Step 3 evidence is collected.

## Layered Architecture Verdict

### Assessment

**Question**: Should we split into layers?

**Answer**: **NO, not yet.**

**Reasoning**:

1. **Current unified approach is working**
   - do2: 5 commands, 4522 lines, fully functional
   - do3: 5 commands + 13 skills, 4634 lines, fully functional
   - No evidence of user confusion or requests for "lightweight" versions

2. **Layering adds complexity without proven benefit**
   - Plugin management complexity
   - Cross-layer dependencies
   - Installation friction
   - Namespace proliferation

3. **Skills (do3) already provide modularity**
   - Skills are composable
   - Skills can be invoked independently via Skill tool
   - Skills enable extension without command growth
   - Skills are the "layer" mechanism, just within a single plugin

4. **Precedent is weak**
   - Visual-iteration exists as separate plugin, but it's a **fundamentally different workflow** (screenshot-based)
   - Promptctl exists as separate plugin, but it's **infrastructure** (hooks), not workflow
   - Do plugins are **cohesive workflow family**, not independent features

### Counter-Arguments

**Argument FOR layering**: "Users who only do TDD shouldn't need to install iterative workflow agents."

**Counter**: Agents are shared (project-evaluator, work-evaluator used by both), so layering saves no code.

**Argument FOR layering**: "5 commands is still too many, each layer could have 2 commands."

**Counter**: 5 commands is not overwhelming. Splitting to 6 layers × 2 commands = 12 total commands across plugins, worse than original 11-command problem.

**Argument FOR layering**: "Progressive disclosure - install base, add layers as needed."

**Counter**: Skills (do3) already provide progressive disclosure within a single plugin.

### Recommendation

**KEEP UNIFIED ARCHITECTURE.**

**Specifically**: **Adopt do3 as canonical plugin.**

**Rationale**:
1. 5-command API is minimal but complete
2. 13 skills provide extensibility
3. Intent detection handles natural language
4. Layering adds complexity without proven user demand

**Future consideration**: If user research shows "I only need X subset" is common, **revisit layering**. But gather evidence first.
