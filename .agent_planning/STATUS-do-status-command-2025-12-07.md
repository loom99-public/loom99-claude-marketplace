### Agent Capabilities Relevant to `/do:status`

#### project-evaluator (PROJECT-WIDE evaluation)

**What it does**:
- Reads PROJECT_SPEC.md/PROJECT.md and entire codebase
- Performs ruthless gap analysis (what exists vs. what should exist)
- Runs software to verify actual functionality
- Traces data flows end-to-end
- Evaluates test suite quality
- Hunts for LLM blind spots (pagination, state, cleanup, error messages)
- **Surfaces ambiguities** - finds signs of "winging it" (magic numbers, assumptions, unclear requirements)
- Detects implementation red flags (TODOs, stubs, fake completeness)

**Outputs**:
- `STATUS-<timestamp>.md` with:
  - Executive summary (% complete, critical issues, test reliability)
  - Runtime assessment (what was tried, what happened, evidence)
  - Data flow verification table
  - Test suite quality score
  - LLM blind spot findings
  - **Ambiguities table** (area, question not answered, how LLM guessed, impact)
  - Implementation assessment table
  - Recommendations (prioritized)
  - **Workflow recommendation**: CONTINUE or PAUSE
- `SUMMARY-project-evaluator-<timestamp>.txt` (one-line summary)

**Modes**:
1. **Standard mode**: Full project evaluation
2. **Research evaluation mode**: Assesses RESEARCH-*.md files for sufficiency

**PAUSE capability**:
- Can recommend PAUSE with clarification questions when ambiguities are blocking
- Triggers auto-research in `/do:plan` workflow

#### work-evaluator (FOCUSED evaluation)

**What it does**:
- Reads latest PLAN-*.md for acceptance criteria
- Acts like a user, not a developer (runtime testing, not just test suite)
- Tries to break the implementation (input attacks, state attacks, flow attacks)
- Follows data through complete lifecycle
- Checks for LLM shortcuts ("happy path only", "looks complete", test-specific hacks)
- **Surfaces ambiguities** at implementation level (magic numbers, defensive code, uncertainty markers)
- Uses chrome-devtools MCP for web UI screenshot evidence

**Outputs**:
- `WORK-EVALUATION-<timestamp>.md` with:
  - Goals under evaluation (from PLAN)
  - Runtime testing (what was tried, what happened)
  - Data flow verification
  - Break-it testing results
  - Evidence (screenshots, logs, errors)
  - Working vs. Not Working assessment
  - **Ambiguities found**
  - **Verdict**: COMPLETE | INCOMPLETE | PAUSE | BLOCKED
  - What needs to change (file:line specificity)
  - Questions needing answers (if PAUSE)
- `SUMMARY-work-evaluator-<timestamp>.txt`

**Modes**:
1. **Standard mode**: Evaluate recent work against PLAN acceptance criteria
2. **Research evaluation mode**: Assesses RESEARCH-*.md for focused technical questions

## Ambiguities Requiring Clarification

### Ambiguity 1: What happens if no PLAN exists? (work-evaluator mode)

**Context**: work-evaluator reads PLAN-*.md for acceptance criteria. What if user runs `/do:status "authentication"` but no PLAN file exists?

**Current behavior in other commands**:
- `/do:it` checks for STATUS/PLAN existence and runs `/do:plan` first if missing

**Options**:
- **Option A**: Fail with error message: "No PLAN found. Run /do:plan first."
- **Option B**: Auto-run project-evaluator instead (fallback to project-wide mode)
- **Option C**: Generate ad-hoc acceptance criteria from PROJECT_SPEC related to the focus area
- **Option D**: Auto-run `/do:plan` first, then work-evaluator

**Recommendation**: Option A (fail fast) or Option D (auto-plan)
- Option A is simpler and clearer to users
- Option D matches `/do:it` behavior pattern but adds complexity

**Impact**: Determines error handling and user experience when PLAN is missing

### Ambiguity 2: Should project-evaluator mode trigger auto-research? (PAUSE handling)

**Context**: In `/do:plan`, when project-evaluator returns PAUSE with ambiguities, it triggers an auto-research loop (researcher agent explores → project-evaluator assesses → decision made). Should `/do:status` do the same?

**Options**:
- **Option A**: YES - Include auto-research loop (matches `/do:plan` behavior)
  - Pros: Resolves ambiguities automatically, consistent with existing workflow
  - Cons: Makes `/do:status` more complex, longer execution time
  - Example from `plan.md` (lines 20-28):
    ```markdown
    **Step 1c: Handle PAUSE (if applicable)**
    If project-evaluator returns **PAUSE** with ambiguities that need resolution:
    1. For each significant ambiguity identified, use the do:researcher agent to explore options
    2. Use project-evaluator (research evaluation mode) to assess if research is sufficient
    3. If sufficient, project-evaluator makes the decision and documents it
    4. Continue to planning with resolved ambiguities
    ```

- **Option B**: NO - Just report ambiguities, don't auto-research
  - Pros: Simpler command, faster execution, pure "status check"
  - Cons: Doesn't help resolve found ambiguities
  - User would need to run `/do:learn` manually for each ambiguity

- **Option C**: Conditional - Auto-research only if args specify (e.g., `/do:status --resolve`)
  - Pros: Flexibility
  - Cons: More complex argument parsing, doesn't match current command patterns

**Recommendation**: Option B (no auto-research) for initial implementation
- `/do:status` semantically is a "check" command, not a "fix" command
- Keeps command lightweight and fast
- Users can run `/do:learn` for specific ambiguities if needed
- Can add Option A behavior later if users request it

**Impact**: Determines command complexity, execution time, and whether `/do:status` is read-only or modifies state via research decisions

### Ambiguity 3: What "next action" should the command recommend?

**Context**: Both command modes end with a summary box showing "Next: [recommendation]". What should this say?

**Current patterns**:
- `/do:plan` → "Next: /do:it or /do:it"
- `/do:it` → "Next: Review STATUS/PLAN or continue"
- `/feature-proposal` → "Next: Run /do:plan to create implementation plan"
- `/learn` → "Next: /do:plan to incorporate into project plan"

**For `/do:status`**:

**Case A: project-evaluator mode, CONTINUE verdict**
- Could say: "Next: /do:plan to create implementation plan" (if gaps found)
- Or: "Next: Review STATUS for details, then /do:plan or /do:it"
- Or: "Next: Project on track, continue with /do:it"

**Case A: project-evaluator mode, PAUSE verdict**
- Should say: "Next: /do:learn to resolve n ambiguities" (if no auto-research)
- Or: "Next: Review ambiguities in STATUS, discuss with user"

**Case B: work-evaluator mode, COMPLETE**
- Could say: "Next: Work complete, run /do:status for full project check"
- Or: "Next: Continue with next work item from PLAN"

**Case B: work-evaluator mode, INCOMPLETE**
- Should say: "Next: Fix issues in WORK-EVALUATION, then re-run /do:status [area]"

**Case B: work-evaluator mode, PAUSE**
- Should say: "Next: /do:learn to resolve n questions" (if no auto-research)

**Case B: work-evaluator mode, BLOCKED**
- Should say: "Next: Resolve blocker (see WORK-EVALUATION), then retry"

**Options**:
- **Option A**: Context-dependent recommendations (different message per verdict/mode)
- **Option B**: Generic recommendation ("See STATUS/WORK-EVALUATION for details")
- **Option C**: No recommendation, just show status

**Recommendation**: Option A (context-dependent)
- Matches pattern of other commands
- Provides clear next step for users
- Helps guide workflow

**Impact**: User experience and workflow integration. Requires defining 6-8 different "next action" messages.

## Risks and Gotchas

### Risk 1: Argument parsing ambiguity

**Issue**: How to distinguish "no arguments" from "empty string argument"?

**Example**:
- User types `/do:status` → $ARGUMENTS is empty or null
- User types `/do:status ""` → $ARGUMENTS might be empty string

**Mitigation**: Test actual behavior in Claude Code. Most slash commands treat both as "no arguments". If uncertain, use string length check or pattern matching.

**Severity**: LOW - Can be resolved during implementation

### Risk 2: work-evaluator requires PLAN acceptance criteria

**Issue**: work-evaluator's effectiveness depends on PLAN-*.md having specific acceptance criteria. If PLAN is vague, evaluation will be vague.

**Mitigation**: Document this in command description or add validation step

**Severity**: MEDIUM - Affects evaluation quality but not functionality

### Risk 3: project-evaluator can be slow on large codebases

**Issue**: project-evaluator performs comprehensive analysis (runs software, traces data flows, checks all files). For large projects, this could take significant time.

**Mitigation**:
- Document expected runtime in command description
- Consider adding "fast mode" in future (skip runtime testing, just file inspection)

**Severity**: LOW - Expected behavior, not a bug

### Risk 4: Overlapping use cases with `/do:plan`

**Issue**: `/do:plan` already runs project-evaluator. User might be confused when to use `/do:status` vs `/do:plan`.

**Distinction**:
- `/do:status` = "Just evaluate, don't plan" (generates STATUS only)
- `/do:plan` = "Evaluate AND plan" (generates STATUS + PLAN, handles PAUSE with auto-research)

**Mitigation**:
- Clear description in command metadata
- Add note in command markdown explaining difference

**Severity**: MEDIUM - User experience issue, can cause confusion
