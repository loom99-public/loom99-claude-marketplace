## 2. False Positive Risk Analysis

### 🚨 CRITICAL RISK 1: Runtime Verification Not Enforced

**project-evaluator.md lines 41-50**:
```markdown
### 1. Does It Actually Work?

**Run the software. Use it like a user would.**

- Start the application/service - does it launch without errors?
- Try the core user flows - do they complete successfully?
- Test with realistic data - does it handle real-world inputs?
- Check error scenarios - does it fail gracefully?

**If you can't use it as intended, it's not complete.** No exceptions.
```

**Problem**: SAYS "run the software" but provides **no mechanism to enforce it**.

**False positive scenario**:
1. LLM evaluator reads code, sees no obvious TODOs
2. Checks grep for red flags (none found)
3. Sees test suite passes
4. Reports "COMPLETE" **without ever running the software**
5. User gets false confidence → ships broken code

**Evidence this happens**: User's core concern #1 - "False positives are a HUGE problem"

**Why it happens**: Instructions say "run" but don't require proof of running.

**Recommendation**: Add enforcement mechanism:

```markdown
### 1. Runtime Verification (REQUIRED)

**CRITICAL**: You MUST provide runtime evidence. No evaluation is valid without it.

**For each user flow tested**:
1. Document exact command/action attempted: `./app login --user=test@example.com`
2. Capture actual output: logs, screenshots, error messages
3. Compare expected vs actual: "Expected: 'Login successful', Actual: 'Error: undefined'"

**Template**:
| Flow | Command/Action | Expected | Actual | Evidence | Status |
|------|---------------|----------|--------|----------|--------|
| Login | `./app login --user=test` | Success message | `Error: auth not impl` | error.log:47 | ❌ |

**If runtime testing impossible** (agent-prompt profile): Mark "N/A - structural validation only"

**If runtime testing possible but not performed**: Evaluation INVALID. Must either run OR explicitly note "Requires manual verification" with user steps.
```

**Impact**: HIGH - Directly addresses user's #1 concern about false positives

### 🚨 CRITICAL RISK 2: "Trust Runtime Over Tests" Easily Ignored

**project-evaluator.md line 275**:
```markdown
- **Trust runtime over tests**: If software fails but tests pass, tests are wrong
```

**Problem**: This is a CRITICAL RULE but buried in line 275 as a bullet point. LLMs pattern-match and can skip bullets.

**False positive scenario**:
1. LLM runs test suite → all pass ✅
2. Briefly attempts runtime → hits error
3. Re-reads tests → "tests are comprehensive, they pass, must be environmental issue"
4. Reports "COMPLETE - all tests pass" **ignoring runtime failure**

**Why it happens**: Tests are easier to verify than runtime (just run `pytest`). Runtime may require setup, data, configuration. LLM takes path of least resistance.

**Recommendation**: Elevate to top-level section and add verification requirement:

```markdown
## Critical Principle: Runtime Trumps Tests

**ALWAYS ALWAYS ALWAYS**: If runtime fails, tests mean nothing.

**Verification**:
1. Run tests → document pass/fail
2. Run software → document works/broken
3. If tests pass BUT runtime fails → tests are WORTHLESS (report this explicitly)
4. If tests fail AND runtime fails → report both
5. If tests pass AND runtime works → report both with evidence

**In STATUS output**:
## Runtime vs Tests Reconciliation
- Tests: 45/45 passing ✅
- Runtime: Login flow works ✅ | Data export fails ❌
- **Verdict**: Tests have BLIND SPOT for data export (tests pass but feature broken)
```

**Impact**: HIGH - Forces explicit runtime vs test comparison

```markdown
If a validation is difficult or taking >30 seconds without progress, **skip it** and note "Requires manual verification" with suggested user steps.
```

4. User assumes "mostly working, just needs quick manual check"

```markdown
   - **Uncertainty blocker** (unclear how to verify): PAUSE and ask user
3. **Track skipped validations** in STATUS:

## Validation Coverage
- Automated: 12/18 (67%)
- Manual required: 4/18 (22%) - [list items]
- Blocked by setup: 2/18 (11%) - [list blockers]

**If >30% validations skipped**: Flag as HIGH RISK evaluation
```

**Impact**: MODERATE - Prevents using "difficult" as blanket excuse

## 3. Confidence Calibration Analysis

### ❌ MISSING: Distinction Between "Verified" and "Appears To Work"

**Current state**: Agents report ✅ or ❌ but don't indicate confidence level.

**Problem**: User can't tell difference between:
- "I ran this and it works" (high confidence)
- "Tests pass so probably works" (medium confidence)
- "Code looks reasonable" (low confidence)
- "Can't verify, user should check" (no confidence)

**Recommendation**: Add confidence levels to all assessments:

```markdown
## Assessment Confidence Levels

Use these markers in STATUS reports:

| Marker | Meaning | Example |
|--------|---------|---------|
| ✅ VERIFIED | Ran it, works | ✅ VERIFIED: Login flow completes successfully (screenshot: login.png) |
| ✅ LIKELY | Tests pass, code reasonable | ✅ LIKELY: Password reset (tests pass, no runtime test) |
| ⚠️ UNCERTAIN | Can't verify, appears incomplete | ⚠️ UNCERTAIN: Email sending (no SMTP config, can't test) |
| ❌ BROKEN | Ran it, fails | ❌ BROKEN: Export crashes (error.log:23) |
| ❓ UNKNOWN | Not evaluated | ❓ UNKNOWN: Admin panel (not tested this iteration) |

**In Executive Summary**: Report confidence distribution:
- VERIFIED: 45%
- LIKELY: 30%
- UNCERTAIN: 15%
- BROKEN: 5%
- UNKNOWN: 5%

**Workflow rule**: If UNCERTAIN + UNKNOWN > 40% → recommend user manual testing session
```

**Impact**: HIGH - Directly addresses user concern #2 about wasted time on failed validations

### ❌ MISSING: "Stop and Ask When Uncertain" Mechanism

**Current**: Agents told to "surface ambiguity" but unclear when to PAUSE workflow.

**project-evaluator.md lines 193-215** (Pausing for Clarification):
- Good framework for WHAT to output when pausing
- Missing WHEN to pause

**work-evaluator.md lines 203-210**:
- Says "recommend PAUSE when ambiguity caused bugs"
- Reactive (after bugs found) not proactive (before wasting time)

**Recommendation**: Add uncertainty thresholds:

```markdown
## When to PAUSE (Stop Workflow)

**Automatic PAUSE triggers**:
1. **Ambiguity with no clear resolution**: Found 3+ magic numbers/assumptions and unclear which are correct
2. **Runtime broken with unclear fix**: Software fails but root cause ambiguous (could be config, could be bug, could be spec)
3. **Multiple valid paths**: 2+ implementation approaches are equally reasonable, need user choice
4. **Validation confidence <50%**: Majority of features UNCERTAIN or UNKNOWN (can't verify without user)

**PAUSE output includes**:
- Specific questions needing answers
- Why continuing would waste time (what would need to be rebuilt)
- Options with tradeoffs for user to choose

**Philosophy**: PAUSE is not failure. It's preventing waste.
```

**Impact**: MODERATE - Makes "stop and ask" actionable

## 4. Validation Enforcement Analysis

### ❌ MISSING: Require Explicit User Sign-Off on Manual Items

**Current**: Agents suggest manual steps but don't enforce user actually did them.

**Problem**:
1. Evaluator: "User should test X manually"
2. Next iteration: Evaluator assumes X was tested (no evidence it was)
3. Repeat for 5 iterations
4. Ship with X never tested

**Recommendation**: Add sign-off mechanism:

```markdown
## Manual Validation Sign-Off

**When evaluation requires manual verification**:

1. Create checklist in STATUS file:
   ```
   ## User Manual Validation Required
   - [ ] Test email sending with real SMTP (steps: X, Y, Z)
   - [ ] Verify PDF export formatting (steps: A, B, C)
   - [ ] Load test API rate limiting (steps: 1, 2, 3)
   ```

2. **Next evaluation**: Check if signed off:
   - Read previous STATUS → extract manual validation checklist
   - If items unchecked → carry forward to new STATUS
   - If items checked → assume validated (proceed with confidence)

3. **Workflow rule**: If manual validation required, IMPLEMENTER cannot proceed until user signs off (marks [ ] → [x])

**Enforcement**: implementer agents check for unchecked manual items before starting work.
```

**Impact**: MODERATE - Prevents manual items from being forgotten

### ❌ MISSING: Automated Test Actually Runs

**Current**: Both agents say "test the tests" but don't enforce it.

**project-evaluator.md line 70**:
```markdown
**Quick test**: Break something obvious, run tests. If they pass, tests are theater.
```

**Problem**: This is ADVICE, not a REQUIREMENT. LLM can skip it.

**Recommendation**: Make it a required step with evidence:

```markdown
## Test Quality Verification (REQUIRED)

**For any project with tests**, you MUST verify tests actually catch bugs:

**Process**:
1. Identify a critical function (e.g., authentication, data validation)
2. Introduce an obvious bug (e.g., return wrong value, skip validation)
3. Run test suite
4. Document result

**Template**:
| Function Modified | Bug Introduced | Tests Run | Result | Verdict |
|-------------------|---------------|-----------|--------|---------|
| `auth/verify.py:login()` | Always return True | `pytest tests/` | 2/45 failed | ✅ Tests catch auth bugs |
| `data/export.py:to_csv()` | Return empty string | `pytest tests/` | 0/45 failed | ❌ Export not tested |

**In STATUS**:
## Test Quality
- Verified: 2/5 modules tested (auth ✅, export ❌)
- Blind spots: Export, pagination, error handling
- Recommendation: Add tests for export, pagination

**If you skip this step**: Mark test quality as "UNKNOWN - not verified"
```

**Impact**: HIGH - Directly prevents trusting worthless tests

### ❌ MISSING: Prevent Proceeding When Validation Incomplete

**Current**: Evaluators report issues, but implementers can proceed anyway.

**No workflow enforcement** that implementer must wait for:
- Manual validations to be signed off
- Critical bugs to be fixed
- Ambiguities to be resolved

**Recommendation**: Add workflow gates:

```markdown
## Workflow Gates (Enforcement)

**Before implementer can proceed**, evaluation must meet:

**Gate 1: Critical Issues Resolved**
- No P0/P1 bugs unfixed
- No BROKEN features unaddressed

**Gate 2: Validation Confidence Threshold**
- VERIFIED + LIKELY >= 60%
- UNCERTAIN + UNKNOWN < 30%

**Gate 3: Manual Debt Bounded**
- Outstanding manual validations <= 5 items
- No HIGH priority manual items >3 days old

**Gate 4: No Active PAUSE**
- If evaluator recommended PAUSE, must be resolved (user answered questions)

**Implementer prompt**: Before starting, read latest STATUS and verify gates passed. If not, STOP and request user intervention.

**Example STOP message**:
> Cannot proceed: Latest STATUS (2025-12-09-043855) shows:
> - Gate 2 FAILED: Only 35% verified (threshold: 60%)
> - Gate 3 FAILED: 8 manual validation items (threshold: 5)
>
> Recommend user manual testing session to clear validation debt before implementation.
```

**Impact**: HIGH - Actually enforces validation instead of just suggesting it
